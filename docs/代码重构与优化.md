# 代码重构与优化

本文记录 2026-10-29 对当前工作区的只读检查结果，供后续规划使用。条目是候选改进，不代表已经实施或证明当前游戏机制有误。实施前应重新核对代码、测试和用户授权；优先保留现有功能、存档、离线能力及计算口径。

## 实施进度

- **已处理**：配速选择器的全局监听在卸载时清理；文字覆盖在隔离环境复现重复触发，现仅在内容变化时写入，并提供浏览器回归。
- **已处理**：配装转换提取为可单独验证的函数，继续复用当前两种计算模型及原有存档格式；补充独立的速度和条件效果检查。
- **已处理**：配速表格在单次请求内复用相同行动窗口的计算；推荐在单次请求内预计算每套遗器贡献，Python 与 JavaScript 同步。
- **已处理**：阿哈角色数字输入防抖并使旧请求失效，等待期间显示计算状态；抽卡计算复用不变的单次和 UP 分布。
- **已处理**：独立网页通过本地模块加载入口执行原始 `ui.js`，不再依赖替换 `export default` 的字面格式；外壳响应式布局由功能显式声明，切页后清理。
- **有意保留**：Python 与 JavaScript 两套计算实现分别服务本机及独立网页，不强行合并不同模型；继续使用双端对照与独立预期验证，不能把对照结果当作真实机制的唯一依据。

以下“现状”和“检查结果”保留为优化前的基线，不表示上述项目仍未处理。独立模块入口目前要求被内联的功能没有相对模块导入；未来引入时需扩展打包器并复验离线运行。

## 总体判断与建议顺序

目录即插件、`ctx.call()` 和数据读取入口让多数功能保持了相对清晰的隔离。不建议为了统一结构而整体重写。优先处理有明确生命周期风险的地方，再处理跨模块转换和经测量有收益的计算热点。

1. 清理配速页下拉菜单的全局事件监听，验证文字覆盖监听的潜在循环。
2. 集中配速配装导入阿哈模拟器时的转换规则，建立独立的输入输出测试。
3. 优化动态速度表格中的重复计算，并按需减少队伍编辑时的重复模拟。
4. 根据实际使用情况优化抽卡概率计算；装备推荐、打包方式和样式依赖可在相关功能修改时逐步整理。

## 生命周期与结构

### 配速页全局监听未清理

- **现状**：[配速页下拉菜单](../modules/honkai-star-rail/features/speed-plan/ui.js)的 `createPicker` 在 `document` 上注册点击和键盘事件；页面卸载逻辑没有移除这两类监听。
- **影响**：反复进入和离开页面时，监听可能累积并持有旧页面对象。这是从代码路径确认的生命周期缺口，尚未进行长时间内存测量。
- **方向**：为每个选择器提供清理函数，或统一使用支持解除的监听机制，并在卸载时调用；覆盖连续切换页面、菜单操作和键盘关闭。

### 配装导入规则跨页面分散

- **现状**：[阿哈后端](../modules/honkai-star-rail/features/aha-speed/api.py)的 `resolve_build` 调用配速查询并返回配装及结果；[阿哈页面](../modules/honkai-star-rail/features/aha-speed/ui.js)的 `unitFromBuild` 再依赖这些字段、装备名称和角色规则，将其转换成模拟器参数。
- **影响**：修改配速返回字段、装备识别或角色条件效果时，需要同步检查页面转换和两个计算路径。例如爻光二魂结界需要避免被固化到常驻速度后再次计入。
- **方向**：把转换集中在可单独测试的入口，明确输入、输出、单位和暂不支持的装备效果。用已有配装存档和独立预期验证导入；桌面与独立网页都要覆盖。配速静态模型与完整战斗模拟的适用范围不同，不应为了去重直接合并公式。

### 双端计算与单文件打包

- **现状**：配速查询和阿哈模拟分别维护 Python `api.py` 与 JavaScript `web_api.js`，以支持本机服务和独立网页。[单文件生成器](../tools/make_web_standalone.py)读取多个功能源码，并通过替换 `export default {` 等文本拼接。
- **影响**：修改计算规则需要同步两个实现；仅调整模块导出写法也可能影响独立网页。现有对拍和离线检查能降低风险，但只能覆盖已有用例。
- **方向**：短期保留双实现，增加共同输入、边界值和游戏机制的独立预期；明确每个入口的数据约定。需要改变打包方式时，再考虑明确的打包入口，保留离线及用户存档验证，不为消除重复而强行统一模型。

### 外壳样式依赖功能内部类名

- **现状**：[外壳样式](../app/style.css)通过 `:has(.aha-sim-wrap)` 和 `:has(.gacha-layout)` 调整侧栏宽度。
- **影响**：功能页内部类名或结构变化可能间接改变外壳布局；这属于需要维护的隐式依赖，不代表当前布局一定有问题。
- **方向**：后续相关页面改造时，考虑由功能明确声明布局需求，并验证宽窄屏和侧栏动画。

### 文字覆盖监听：待复现

- **现状**：[外壳文字替换](../app/app.js)监听整个页面的子节点变化，变化后重新扫描并写入覆盖文字。
- **待确认**：存在覆盖文案时，写入是否会再次触发监听、造成重复工作或卡顿；本次仅代码分析，未用实际覆盖配置复现。
- **方向**：先在隔离数据环境复现并测量；若确认有问题，再考虑只处理新增节点、跳过未变化内容或合并更新。验证文字覆盖、页面切换和动态加载。

## 计算与交互性能

以下计时为本机一次直接调用 Python 的参考值，不含页面渲染和请求耗时，不代表所有设备或场景。优化前应先用目标设备和实际配置重新测量。

### 动态速度表格重复计算

- **现状**：[配速计算](../modules/honkai-star-rail/features/speed-plan/api.py)逐模式、动数、轮次生成表格。多个模式有相同的行动值窗口；带开大加速等动态效果时，每格通过二分调用行动模拟。
- **检查结果**：当前数据下约 200 个表格单元，对应约 88 组不同的「动数 + 行动值」；一次动态配置调用约 1.2 万次模拟。本机示例静态约 0.3 毫秒，动态约 40 毫秒。
- **方向**：在单次计算中按完整影响条件复用等价结果，不跨配置使用失效缓存；与未优化结果比较所有表格、目标与边界值。需要同步检查 JavaScript 版本及浮点边界。

### 队伍编辑连续触发模拟

- **现状**：[阿哈页面](../modules/honkai-star-rail/features/aha-speed/ui.js)数字框的每次输入都会发起模拟。页面会丢弃过期结果，但已发出的请求仍可能执行。
- **方向**：对连续输入加入短暂防抖，保留最终值及时计算；验证快速输入、切换队伍、离开页面及慢请求乱序。不可使用旧结果冒充当前结果。

### 抽卡概率的重复卷积

- **现状**：[抽卡计算](../modules/honkai-star-rail/features/gacha/api.py)计算多个目标时反复构造相同的单次概率分布并做卷积。
- **检查结果**：本机角色池目标 7 个约 40 毫秒、20 个约 0.39 秒；数量较大时更值得关注。
- **方向**：复用不变的单次分布和重复子计算，保留大小保底、初始垫抽和完整概率精度；以独立预期、概率总和、分位数及边界输入验证。

### 自动推荐中的重复装备贡献

- **现状**：[推荐计算](../modules/honkai-star-rail/features/speed-plan/api.py)在组合循环中重复计算部分装备贡献。
- **检查结果**：本机示例约 7105 个组合耗时 13 毫秒，目前优先级较低。
- **方向**：可预计算不随组合改变的贡献，并保持排序、去重、条件触发和候选范围完全一致；先测量再决定是否实施。

## 实施与验收

### 开发检查与技术栈（2026-10-29）

- 项目继续使用 Python 后端和原生 JavaScript；目前的单文件离线导出与插件加载可以满足需求，不为引入框架或打包器而迁移。若模块依赖、构建性能或调试体验出现具体瓶颈，再评估构建工具；离线导出的 Blob 模块不支持未经处理的相对模块导入，新增依赖时应同时验证服务端与离线模式。
- 新增独立的 GitHub Actions 验证流程，分支推送、拉取请求和手动运行时检查类型、单元测试、双端对拍、配装转换及隔离浏览器；它不打包也不发布。原有发布工作流在打包前运行同一组检查，失败则不继续。
- 类型检查是渐进式的：目前仅检查阿哈页面及其浏览器全局声明，不表示全项目已具备完整静态类型覆盖。开发时先执行 `npm ci`，再执行 `npm run typecheck`；这些是开发依赖，不改变运行时依赖。
- 本机运行完整单元测试时，Windows 可设置 `PYTHONUTF8=1` 和 `PYTHONIOENCODING=utf-8`，避免子进程输出按 GBK 解码。浏览器检查可运行 `pwsh -NoProfile -File tools\verify_ci_ui.ps1`，需要 Python、Node.js 22 或更高版本及 Microsoft Edge；脚本使用独立临时存档和浏览器配置，不读取真实存档。
- 双端对拍加入重复角色和阈值边界；仍需以独立游戏机制依据和单元测试确认结果，双端相同本身不能证明机制正确。

- 本文只记录方向，不扩大任务或发布授权。实施前分别确认具体范围、当前代码和存档兼容性；不要改动 `userdata/` 或刷新基准来掩盖差异。
- 按 [项目约定](../AGENTS.md)选择适用的功能开发、跨模块一致性、战斗模拟和界面验证流程；先做最小相关测试。
- 涉及配速双端时运行 `node tools\check_web_port.mjs`；涉及阿哈双端时运行 `node tools\check_aha_port.mjs`。对拍证明实现间一致，不单独证明真实游戏机制正确。
- 涉及界面时用独立用户数据与浏览器配置，检查实际输入、状态、切换和错误；涉及单文件时核对离线运行和存档。按影响范围决定是否运行完整单元测试。
